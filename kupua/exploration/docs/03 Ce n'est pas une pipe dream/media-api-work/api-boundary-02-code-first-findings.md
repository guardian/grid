# API boundary 02: source-first findings

18 September 2026. Research only; no architecture approved or implementation commissioned.

Evidence labels: **S** source; **T** test read, not execution; **E** experiment; **O** operator constraint; **H** hypothesis/proposed contract. File links identify current deciding code, not historical plans.

## 0. Decision

**Keep Kupua's navigation in the browser; put permission checks and bounded data reads in media-api. Prove a lightweight ordered-keys capability before commissioning the remaining implementation.** Do not replace the experience with pagination, fetch every image to simplify the client, or start a separate service.

In plain terms, Grid would return compact navigation records without preparing and signing full image responses merely to locate those images.

Candidate B below is the preferred proof target, with **medium confidence**. Its limited saving is avoiding separate Scala implementations of collectors that already work in TypeScript: building position maps, collecting bounded ranges and accumulating keyword buckets. It does **not** eliminate the underlying sorting, counting, aggregation or image-enrichment work. Roughly the present breadth of backend capability remains necessary.

The recommendation includes the full acceptance floor, but **complete API-only feasibility and unchanged performance are not established**. The hardest pending fact is whether a policy-checked, lightweight read boundary preserves positional correctness and completion time without relocating large scans or adding excessive round trips. If that proof fails, retain the conservative operation-oriented baseline, not an unapproved feature reduction. D3's completed amendment/review process is not reopened by this research.

## 3. Boundary and alternatives

### Hard question and result

**H tested:** could existing image pages plus more browser indexing remove specialised navigation capabilities? The experience still needs arbitrary indexed positions, bounded memory, ties/missing values, selection and fast recovery. The hypothesis fails if equivalent indexing requires substantially more serial requests or processing full images merely to obtain keys.

**S/E01:** it fails. [Shared validation](../../../../../media-api/app/lib/elasticsearch/ElasticSearchModel.scala#L409) caps image pages at 200; [D3](../../../../../media-api/app/lib/elasticsearch/ElasticSearch.scala#L755) rejects offsets and projects images, and its [controller](../../../../../media-api/app/controllers/MediaApi.scala#L853) enriches every returned hit. A 65,000-entry map therefore needs at least **325 enriched pages**, versus current 10,000-entry source-free chunks. Paging through E02's entire corpus would need at least **6,140** image pages. Discarding each page afterward saves retained browser image memory, not ES work, decoding, signing or round trips. Extending full maps to all large sets moves the enumeration problem; it does not remove it. **Reject existing-routes-only composition as a preserved-performance solution.**

Keyword weakness is more specific than "keyword mappings are broken." Source maps Credit/Source as keywords and dimensions as integers ([mappings](../../../../../common-lib/src/main/scala/com/gu/mediaservice/lib/elasticsearch/Mappings.scala#L112)); configured leaf mappings still need checking. The costly fallback enumerates vocabulary, then obtains a page and exact landed rank. E02's complete 8,769-key vocabulary worked; it did not exercise the 50,000-key cache ceiling. The eight-second guard is checked **between** requests, not a hard deadline. No evidence here attributes that weakness to rendering or proves moving the loop server-side fixes it.

### Minimal contracts

**H:** these are capability contracts, not a generic ES proxy or a commitment to one route per row. Existing code supplies query/policy, field-sort, projection and response machinery; bounded adapters and missing query shapes remain real new Grid work.

**Policy and ownership.** One endpoint-local admission layer must derive the effective query using Grid's parser, default hiding, free/rights/syndication policy and authenticated principal. Maps, ranks, buckets and IDs can disclose information too. D3 [scopes parsed deleted intent before hits/totals](../../../../../media-api/app/controllers/MediaApi.scala#L879); existing GET uses a different [raw query check](../../../../../media-api/app/controllers/MediaApi.scala#L588). Thus `GET /images?length=0` is not an unconditional replacement for companion counts. Reuse its execution machinery under the admitted predicate without changing legacy GET behavior incidentally. Preserve existing [POST tier denials](../../../../../media-api/test/controllers/MediaApiTest.scala#L112) and [single-image visibility](../../../../../media-api/app/controllers/MediaApi.scala#L168).

The server owns allowed sort meaning, aliases and query execution; TypeScript may retain `SortValues`, maps and interpolation. Validate client-resolved clauses against the supported semantic sort, including unique ID suffix, nested path and max-mode, rather than accepting arbitrary sorts/scripts. A separate Kupua semantic builder, if needed, must not change [Kahuna's real sort caller](../../../../../kahuna/public/js/services/api/media-api.js#L79) or shared legacy defaults. Returned hit tuples remain authoritative; approximate seek anchors are explicitly different. Missing authoritative alias tuples require lookup, not treating absent raw metadata as a genuinely null sort value.

**Views and continuation.** Today the [first page and PIT open run in parallel](../../../../src/stores/search-store.ts#L2269); maps open another PIT; rank, range walks and profiles do not use that PIT. Preserve this distinction. Bind requests to normalized query/sort identity **and a declared scope variant**: frozen browsing, live polling, self-excluded typeahead, AI-result IDs or collection defaults. This prevents accidental predicate drift without promising cross-operation snapshot exactness.

**H:** the server opens only its configured image target and issues a bounded, principal-associated read handle. New requests reapply policy; no client-selected index or arbitrary PIT target. Renew ordinary one-minute PITs, propagate refreshed IDs, close superseded/map-complete contexts, and make close idempotent. Caller generations own overlapping requests; abandoned work must stop or hit endpoint budgets. Explicit expiry allows bounded reacquisition/live recovery using portable tuples, not ES fallback, and not bypassing refusals. The handle representation/admission limits need agreement; a durable session store is not required.

**Errors.** Invalid, refused, expired and unavailable are distinct from successful empty data. Cancelled/failed ranges are not committed; unsuccessful hydration retains membership. Optional enrichment/quotas may remain absent, but loss of the sole image source cannot masquerade as zero results. Existing metadata/date routes only accept their narrower aggregation params and return different totals/shapes ([implementation](../../../../../media-api/app/lib/elasticsearch/ElasticSearch.scala#L630)); API naming alone is not reuse evidence. Current raw-source-by-ID is also not a bulk keys route.

### Candidate comparison

All candidates below retain the same required workflows; none assumes production capacity from source.

| C: server-owned browse windows | Server computes seeks/ranks/neighbors and can retain maps, reducing wire exchanges. The real reduction worth testing is B's reuse of bounded collectors. It is not "all navigation becomes one search endpoint." Combining counts with first-page hits could save duplicate work but also delay first-visible data; it is not assumed here. Nor is replacing live range selection with a slice of an older map assumed equivalent.
