## 2 Material Findings

### A. Date filters and chip deletion

**Declared source boundary and deciding question.** Follow DateFilter and the CQL delete event through URL canonicalization, history, store parameters, and ES/CQL clauses. The deciding question was whether a date chosen in the UI has the same calendar/boundary meaning as the request, and whether chip deletion preserves the completed query/history contracts.

DateFilter keeps draft state until Filter, while presets apply immediately. `Anytime` clears `dateField` and all six bounds. Save/replacement clears the five non-selected bounds. Cancel, outside click, and Escape restore the URL-backed draft without navigation. `useUpdateSearchParams` normally pushes a fresh history key; URL sync then clears removed store keys, clears selection for a real query navigation, and starts one search. These are intentional current contracts ([DateFilter.tsx](../../../../src/components/DateFilter.tsx#L193-L352), [useUrlSearchSync.ts](../../../../src/hooks/useUrlSearchSync.ts#L145-L221), [useUrlSearchSync.ts](../../../../src/hooks/useUrlSearchSync.ts#L430-L499)).

Top-level `since`/`until`, `takenSince`/`takenUntil`, and `modifiedSince`/`modifiedUntil` become exclusive `gt`/`lt` ranges. Date-only strings are normalized to UTC midnight by the ES builder ([es-adapter.ts](../../../../src/dal/es-adapter.ts#L443-L479)). CQL `usages@<added` and `usages@>added` are a separate nested syntax using inclusive `lte`/`gte` clauses ([cql.ts](../../../../src/dal/adapters/elasticsearch/cql.ts#L276-L296)); deleting or composing a CQL chip must not be treated as editing a top-level date bound.

#### P32-A1: DateFilter emits local-calendar instants for UTC-bound top-level dates

DateFilter creates presets with `startOfToday()` and custom From/To values with local midnight/end-of-day before converting them to ISO. The request builder treats date-only bounds as UTC midnight and applies exclusive bounds. A user selecting the same visible calendar date therefore sends a timezone-dependent instant, and a URL containing a UTC-midnight bound can display a different local calendar date. This is a current source defect, not a migration feature request. The smallest discriminating check is a mounted DateFilter at a negative-offset timezone: select `2026-03-20`, assert the URL bound and the displayed date, then compare the generated ES range to the UTC-midnight contract. No such check was run.

#### P32-A2: Invalid URL date values can throw during DateFilter render

The URL schema accepts arbitrary strings. `formatDateShort` catches invalid ISO values, but `toDateInputValue` calls `format(parseISO(value), ...)` without a guard. A malformed externally supplied `since`, `until`, or field-specific bound can therefore throw while rendering the date input before the request layer can classify it. The smallest check is a mounted DateFilter with `since=not-a-date`; no runtime check was run. This is separate from CQL date syntax and from KUP-011.

Chip deletion is not a new actionable defect. The CQL custom element owns deletion; the wrapper only detects the delete handle for the `chip-remove` trace ([cql-chip-delete.ts](../../../../src/lib/cql-chip-delete.ts#L1-L9), [CqlSearchInput.tsx](../../../../src/components/CqlSearchInput.tsx#L250-L270)). The effective-query helper strips incomplete `key:` chips while preserving quoted literal text and dotted/quoted keys ([cql-effective-query.ts](../../../../src/lib/cql-effective-query.ts#L1-L46)). SearchBar creates the typing entry/debounce, and URL sync claims `chip-remove` only for a user query-only navigation ([SearchBar.tsx](../../../../src/components/SearchBar.tsx#L115-L177), [perceived-navigation.ts](../../../../src/lib/orchestration/perceived-navigation.ts#L1-L17)). Native date inputs are excluded from list navigation; the CQL host is deliberately not treated as native ([dom-utils.ts](../../../../src/lib/dom-utils.ts#L18-L36)). The focused test only checks the pure composed-path predicate ([cql-chip-delete.test.ts](../../../../src/lib/cql-chip-delete.test.ts#L1-L15)); the inherited PP9 record is execution evidence, not a new current run.

### B. Cost and syndication display

**Declared source boundary and deciding question.** Follow CostBadge, SyndicationBadge, their explanation helpers, and the supplied baseline/overlay values through deriveImage and actual grid/detail consumers. The deciding question was whether null, false, zero/empty, absent, stale, and server-overlay values produce labels consistent with the effective state, without treating display as authorization.

The baseline cost chain is restrictions -> configured category cost -> free agency supplier/quota -> pay. Missing quota is deliberately quiet and leaves a free supplier free ([calculate-cost.ts](../../../../src/lib/cost/calculate-cost.ts#L22-L71), [quota-store.ts](../../../../src/lib/cost/quota-store.ts#L1-L76)). `deriveImage` uses nullish overlay precedence: overlay cost, validity, invalidReasons, usageRights, syndicationStatus and usages win when supplied; false and empty objects/arrays are retained. `noRights`, however, is always computed from the ES baseline usageRights ([derive-enriched-image.ts](../../../../src/lib/derive-enriched-image.ts#L86-L123)).

Grid cells use the merged image. Free cost is hidden; non-free cost is rendered with a no-rights variant when `enriched.noRights` is true. The field-registry badge renderer makes the same choice ([ImageGrid.tsx](../../../../src/components/ImageGrid.tsx#L215-L229), [ImageGrid.tsx](../../../../src/components/ImageGrid.tsx#L398-L424), [field-registry.tsx](../../../../src/lib/field-registry.tsx#L341-L390)). Cost tooltips explain cost/restrictions, but the no-rights branch ignores lease-prefix/restriction arguments ([CostBadge.tsx](../../../../src/components/CostBadge.tsx#L85-L183)). Syndication status is unsuitable without acquired rights, then sent > queued > blocked > review; the badge hides unsuitable/null and maps the remaining status to a reason string ([calculate-syndication-status.ts](../../../../src/lib/syndication/calculate-syndication-status.ts#L65-L102), [SyndicationBadge.tsx](../../../../src/components/SyndicationBadge.tsx#L9-L31), [syndication-reason.ts](../../../../src/lib/syndication/syndication-reason.ts#L1-L30)).

#### P32-B1: Overlay usageRights and cost can disagree with the no-rights badge state

Expected: when a server overlay supplies effective usageRights/cost, the displayed badge and explanation should describe that effective state. Actual: `deriveImage` overlays usageRights and cost but retains `noRights` from the ES baseline. A baseline image with no category plus an overlay with a valid category can therefore render a no-rights variant for a non-free cost, or hide the badge when the overlay cost is free; the detail rights label simultaneously uses the overlay category. The existing derive test explicitly preserves this baseline-only `noRights` behavior, so this is a known contract inconsistency rather than an unobserved claim ([derive-enriched-image.test.ts](../../../../src/lib/derive-enriched-image.test.ts#L178-L205)). Smallest check: pure derive plus the existing grid/field-registry renderers using baseline no-rights and overlay free/pay/category cases. Likely affected assertions are the `noRights` precedence test and badge renderer cases; no assertion should be weakened without choosing the owner of effective rights.

#### P32-B2: Quota and time-derived policy can remain stale for a stable image reference

Expected: a quota response or lease-time boundary should eventually change a visible derived badge when the same image remains mounted. Actual: quota is a module-level one-shot map with no subscription, and `useEnrichedImage` returns its memoized result when image and overlay references are unchanged. The same mechanism also freezes time-derived syndication/lease calculations for that hook instance. The smallest check is a mounted hook with a stable image/overlay reference, then a quota-map or clock change and a rerender; no check was run. This is display freshness, not authorization, and does not justify per-image network requests.

#### P32-B3: An overlay-less refresh does not clear an old overlay for the same ID

Expected: an API overlay is absent when a new result omits it, so the ES baseline is visible for that result. Actual: `upsertEnrichment` retains prior entries, and a fresh store commit only replaces the map when `result.enrichment` is truthy; a direct-ES or fallback result with `undefined` enrichment does not clear an old same-ID entry ([enrichment-store.ts](../../../../src/stores/enrichment-store.ts#L47-L79), [search-store.ts](../../../../src/stores/search-store.ts#L2450-L2465)). The consequence is stale server cost/validity/syndication/usages presentation after an overlay-less refresh. Smallest check: seed one overlay, commit the same ID through an overlay-less direct-ES result, and assert the effective view falls back to baseline. Existing enrichment replacement/upsert tests cover each primitive but not this cross-mode publication transition ([enrichment-store.test.ts](../../../../src/stores/enrichment-store.test.ts#L16-L64)).

### C. Measurement trustworthiness

**Declared source boundary and deciding question.** Inspect trace producers, phase consumers, correlated calculation, harness validation/aggregation, scenario/config boundaries, canonical rows, and dashboard comparability. The deciding question was whether each row measures the stated action with one owner, correlated phases, honest completion, and preserved topology/cache/sample limits.

Trace IDs correlate action phases, and current search/seek publication uses generation/current-owner guards before `t_store_ready` ([perceived-trace.ts](../../../../src/lib/perceived-trace.ts#L34-L118), [search-store.ts](../../../../src/stores/search-store.ts#L2112-L2140), [search-store.ts](../../../../src/stores/search-store.ts#L2430-L2450)). The September 22 canonical direct-ES rows are inherited four-run records with scenario revision 2, pinned cutoff, uncontrolled browser cache, one worker, and direct-ES route; the separate current temp JSONL files are one captured set, not a new campaign.

#### P32-C1: `dt_ack_ms` is labeled as visible response but is emitted before visible response

The short-suite documentation calls `dt_ack_ms` the time to the first DOM-visible change. Actual `t_ack` is emitted synchronously by store search/seek ownership before the network result and before the visual observers append `t_first_visible_frame`; the metric is an acknowledgement/request-start boundary, not a DOM-visible boundary. This is visible in the source ordering and in canonical rows where acknowledgement and first-visible values are materially different. Smallest correction check: use a mutation/observer or trace a deliberately delayed render and assert `t_ack` is not presented as first-visible latency. No campaign rerun is justified merely to establish this semantic correction.

#### P32-C2: Correlated phase validation does not enforce chronology

The calculator checks one start, missing phases, duplicates, and finite timestamps, but it does not reject a required phase emitted before `t_0`, a negative duration, or a terminal phase before its status phase. Such a row can be accepted with negative elapsed values. No current canonical row was asserted to contain this failure; classify it as a harness correctness defect with medium confidence. Smallest check: a pure calculator fixture with out-of-order `t_store_ready`/`t_0` and an assertion that the row is rejected. Existing duplicate/missing phase tests would remain unchanged and should be extended, not weakened.

The remaining measurement contracts are preserved as limits, not bugs: PP10 is explicitly a background diagnostic; JB5 begins at fullscreen exit and does not measure the preceding twenty traversal identities; route capture records successful route classes, not deployed topology; environment comparability preserves scenario revision and declared cache class but `uncontrolled-browser-cache` does not reveal actual cache contents. Existing recorded results therefore remain useful evidence with their sample-count, origin, cache, scenario, and topology limits.
