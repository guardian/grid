# P31: Restore Correctness With the Fast Path Preserved

20 September 2026. Strong reviewer, role `bounded-design`. Same authorized P31 assignment retried after a transport launch failure, not another investigation. Report only. Recommendations **UNAPPROVED**; proposed behavioral checks **UNEXECUTED**.

## 1. Decision

**Recommend conditional re-ranking inside the existing restore owner, before the unchanged centred helper.** Start saved-tuple rank and target lookup together. Select the response tuple when present; reuse the speculative rank only when that complete tuple equals the saved tuple. Otherwise issue one rank for the selected tuple. Publish placement in the coordinate regime of the retained session total, targeting the actual inserted image's published ordinal.

This resolves the design question in [candidate 11 section 12](api-boundary-11-candidate-plan.md#L663) and [preserved P29 C3](api-boundary-12-plan-challenge.md#L113). It is a proposed resolution of [KUP-024](../../bug-backlog.md#L163) and [KUP-025](../../bug-backlog.md#L173), not a completed repair. They gate the **migrated restore consumer using S3a/S5 and its S10 acceptance**, not standalone server rank/window methods.

**Smallest proposed production patch:** the imports and `restoreAroundCursor` in [search-store.ts](../../../../src/stores/search-store.ts#L3835). Import the existing `isTwoTierFromTotal`; change rank selection, local ownership checks and target publication. Keep `_loadBufferAroundImage`, its result shape, `alignBufferStart`, the hooks, cache, DAL signatures, adapters and server code unchanged. Primary regression home: the existing restore/cancellation/fill groups in [search-store.test.ts](../../../../src/stores/search-store.test.ts#L2419), with PIT-specific extensions only in [search-store-pit.test.ts](../../../../src/stores/search-store-pit.test.ts#L137).

No always-serial lookup/rank default, locate endpoint, map-as-authority shortcut, global geometry rewrite, new module/abstraction, historical snapshot, exact continuation totals or approved performance concession follows.

## 2. Material Findings

P18 already distinguishes cached-cursor restore from snapshot restoration through ordinary search ([P18 F2/F3](api-boundary-09-p18-history-identity.md#L26)). This brief changes only the former consumer. Lookup and rank are live; neighbours can use the existing PIT. Selecting one input tuple does **not** make these operations a common historical snapshot or freeze metadata/deletions. Existing shared-query admission must also agree: tuple coherence cannot compensate for different admitted predicates between rank, lookup and pages.

### Recommended Algorithm

1. Preserve suppression and cursor-null branches. A null **cursor** delegates to existing `seek(cachedOffset)`; a valid tuple with a null **element** does not. Capture the current search generation, raw/frozen params and existing range signal when the restore takes ownership. Do not mint a new global generation or use `_seekGeneration` as a request token.
2. Immediately start `countBefore(params, savedTuple, signal)` and the existing ID-filtered, one-hit `searchAfter(..., null, null, signal)`. Attach success **and rejection** handlers to the saved-rank promise at creation, producing an inert local outcome. Those handlers must not mutate state, log, recover or publish. Await lookup first; do not wait for an irrelevant rank merely to collect both outcomes.
3. After the ownership check, an absent target stops this restore: clear loading only while current, keep the existing buffer/total and do not call the centred helper or seek. The already-started rank remains handled but irrelevant, even if pending or rejected. Do not abort the shared controller merely to dispose of that speculative result.
4. Select `targetResult.sortValues[0] ?? savedTuple`, as today. Equality means equal lengths and equal corresponding primitive values, including all physical tie values and nulls. Use the existing normalized tuples; do not strip fields or parse dates here. If equal, await/use the saved-rank outcome. If different, start and await **one** `countBefore` for the selected tuple without awaiting the obsolete outcome. Never substitute a successful old rank when the selected rank fails. Do not repeatedly look up or re-rank to chase live changes.
5. Once the selected rank succeeds and ownership still holds, call the unchanged `_loadBufferAroundImage(targetHit, effectiveTuple, selectedRank, ...)`. Its forward and backward pages remain parallel and receive that same tuple. The helper needs the selected rank for its current trimming/alignment; it does not currently expose raw pages for later alignment.
6. After the helper and a final ownership check, sample `publishedTotal = get().total` once. Set `publishedTargetOrdinal = buf.bufferStart + buf.targetLocalIndex`. Publish that total and use `isTwoTierFromTotal(publishedTotal) ? publishedTargetOrdinal : -1` for `_seekTargetGlobalIndex`. Preserve `buf.targetLocalIndex` as the local target and `buildPositions` as the position-map builder. For explicit focus, store that same published ordinal as `_focusedImageKnownOffset`.
7. Retain the existing synchronous commit sequence: retain the combined response tuples under the captured search key, upsert the helper's merged enrichment, then publish results/origin/cursors/positions/total/focus and increment `_seekGeneration` once. There is no provisional old-rank buffer or second correction publication. Keep the existing PIT-null precedence and post-publication `_topUpScrollModeBuffer` call.

**Actual target, not just a plausible number:** in a coherent stable fixture the published ordinal equals the selected count-before rank. Assert both that equality and the identity at `results[_seekTargetLocalIndex]`; internally consistent positions alone could merely reproduce the wrong saved rank. Deriving the target from the helper's actual inserted position also respects its existing nonnegative clamp and [column trimming](../../../../src/lib/buffer-column-align.ts#L51). If independent live reads disagree near that clamp, this does not certify a new exact global snapshot rank; it prevents the scroll target from naming a different slot than the one just published. No geometry algorithm changes or separate live-drift bug claim is needed.

### Exact Ordering and Counts

Counts below are **logical DAL calls dispatched by restore**, after an existing session is available, not HTTP latency, ES query work, startup/map/PIT-opening calls or background fill. `R_saved` is the initial rank; `Lookup` is the ID-filtered page; `R_effective` is the conditional rank; `Forward` and `Backward` are the two calls inside the current helper. Each neighbour call requests `floor(PAGE_SIZE / 2)`; even an empty edge side is still requested.

| Case | Required ordering | Restore calls |
| --- | --- | --- |
| Present target, unchanged complete tuple | Start `R_saved` and `Lookup` together; after both usable results, start `Forward` and `Backward` together. | **4**, the current successful fast path; no extra rank, lookup or map request. |
| Present target, lookup has no tuple | Select saved tuple; same join and two helper calls. | **4**. This is the retained fallback contract, not proof of fresh tuple knowledge. |
| Present target, changed tuple | Start `R_saved` and `Lookup` together; `Lookup -> R_effective -> (Forward parallel Backward)`. Never join obsolete `R_saved` back into the dependency chain. | **5**: exactly one conditional extra rank. `R_saved` may still be running when later work starts. |
| Missing target | Start the initial pair; stop on the current empty lookup, independent of the rank outcome. | **2 started**, zero helper calls, zero restore-triggered seek. |
| Lookup failure or selected unchanged-rank failure | Initial pair already started; do not invoke the helper. | **2**, plus at most one existing recovery-action invocation if current and applicable. |
| Selected changed-rank failure | Initial pair plus `R_effective`; no helper. | **3**, plus that qualified recovery action. |
| Neighbour failure | Helper already dispatched both directions after the selected rank. | **4 or 5**, plus that qualified recovery action; no new restore-level retry loop. |
| Superseded restore | Discard the issued prefix; start no later phase after observing ownership loss. | Issued prefix is **2, 3, 4 or 5**, depending on the phase; **zero** new recovery/publication by the stale restore. |
| Suppressed restore / no saved cursor | Suppressed: return. Cursor-null: delegate once to existing seek. | **0 restore DAL calls**; cursor-null additionally invokes one seek action. |

**Relevant retries, counted separately:**

- [The expiry-aware wrapper](../../../../src/stores/search-store.ts#L1416) does not add a request itself. It prevents resending a cleared PIT and preserves a timely `pitId: null`, including when the other direction later fails.
- [Strangler](../../../../src/dal/strangler-adapter.ts#L63) retries an explicitly expired PIT page once without that PIT. For this restore's two concurrent neighbour pages, the expiry-only case adds **zero, one or two page attempts** to the four/five-call path; both pages may have been dispatched before the first clears the PIT. Target lookup is PIT-less, and rank has no PIT argument. The tuple and selected rank are not reacquired on this retry. Failure of that retry propagates; it does not re-enter the same catch for another recovery cycle.
- [Direct paging](../../../../src/dal/es-adapter.ts#L1048) has its existing one PIT-less replay on the recognized PIT failure. Current hybrid `unavailable` handling can instead add one direct-ES fallback for the affected API call, whose direct paging may itself take that PIT replay. These are distinct existing adapter paths, not permission for new unconditional retries or an API-only ES fallback. Counts here describe the inspected adapter layer, not hidden infrastructure attempts.
- The existing generic restore catch delegates once to `seek(cachedOffset)`; this proposal adds ownership checks, not a new recovery algorithm. The [shallow branch](../../../../src/stores/search-store.ts#L2928) then performs one page call. The inspected mapped branch uses one or two page calls depending on cursor/backward availability. Other deep-seek estimation/correction work is delegated unchanged and has no single fixed call count asserted here. Thus **four/five is not a claim about every recovery journey's total**. KUP-010 governs the separate refusal/API-only constraint below.
- Small-result [top-up](../../../../src/stores/search-store.ts#L1139) runs only after successful publication, using existing forward-then-backward extension actions and its progress/deadline bounds. Its data-dependent page calls are additional, not part of the four/five-call landing. It issues no new restore lookup/rank. Indexed/high-total cases do not enter it; test primary counts before top-up or in those regimes. Keep the existing 700-item fill/convergence assertions.

The unchanged case retains the same data dependencies and request count, not a newly measured timing guarantee. The changed case adds one selected rank and may overlap an unfinished obsolete rank; its concurrency/resource and latency effects are **unmeasured and unapproved**. No performance concession follows from arithmetic.

### Ownership, Publication and Exceptions

- **Current owner:** use the captured range signal plus the captured `_searchGeneration`. [Search](../../../../src/stores/search-store.ts#L2049) advances that generation and [aborts prior range work](../../../../src/stores/search-store.ts#L2111); a later [seek](../../../../src/stores/search-store.ts#L2833) or restore aborts the range signal. An ordinary URL sort reaches [the existing search call](../../../../src/hooks/useUrlSearchSync.ts#L397). No new request-owner abstraction is necessary.
- **Every exit matters:** check ownership after lookup, after whichever rank is selected, after helper completion, and at the beginning of the catch before logging, loading changes or fallback. A non-AbortError rejection after cancellation must not clear a newer owner's loading flag or initiate a seek. Do not add an unconditional `finally` that clears loading. Stale outcomes write no results, positions, tuples, enrichment, focus, cursors, seek generation or total.
- **Speculation is local:** attach the rejection handler immediately, including when lookup fails or returns no target. Once unselected, the saved rank's success/failure cannot affect restore, even if it settles after successful publication or after a newer search. No new rank-only controller is needed; do not abort the shared controller and cancel useful work. If selected, its error remains a real selected-operation failure, not an implicit rank of zero.
- **PIT ownership stays where it is:** preserve the wrapper's signal checks and early expiry clearing. A successful sibling must not revive a cleared PIT. Do not treat `_pitGeneration` as the restore generation; background small-set top-up retains its existing total/PIT-generation ownership rather than acquiring a new global action policy.
- **Missing versus failed:** use target-hit absence, not `total === 0`, to choose standalone degradation. A missing response tuple selects the existing saved-tuple fallback; a tuple containing null remains valid. Do not convert selected refusals/failed ranks into empty successful geometry, retry them as obsolete speculation, or publish target enrichment before the complete landing.
- **Restrained recovery scope:** retain current generic recovery behavior except for the new current-owner guard. That does not declare current hybrid refusal recovery acceptable or close KUP-010. Before S10, approved construction/dispatch must make the composed recovery incapable of browser ES; a correctly pure-API datasource can satisfy this without a separate broad store repair. If a new nullable/typed failure contract changes selected-read outcomes, its owner must define that mapping before activating this consumer. P31 does not invent a failure taxonomy or reopen a security/recovery batch.
- **No universal action-ownership claim:** [AI-only sort](../../../../src/hooks/useUrlSearchSync.ts#L377) takes `resortAiBuffer`, not ordinary `search()`. This brief's sort-supersession guarantee is for the ordinary search owner. P18's pending input/Home/deferred-geometry qualifications remain independent ([P18 F4/F5](api-boundary-09-p18-history-identity.md#L47)); this local guard does not bind arbitrary future callbacks to history entries. No AI/debounce/history state-machine change is proposed.

### Plausible Local Alternatives

| Option | Assessment |
| --- | --- |
| **Conditional rank, then existing helper** | **Recommended.** Four-call unchanged path remains parallel; changed path is one extra rank and one final landing. Existing helper owns all alignment and tuple/enrichment assembly. |
| Always look up, then rank, then helper | Four calls but a new serial dependency on **every** successful restore. The unchanged tuple does not need that dependency; reject as the default. |
| Overlap corrected rank with neighbour fetching, then rebase before publishing | Plausible local optimization. [Sort-around-focus already has conditional post-fetch alignment](../../../../src/stores/search-store.ts#L1778), so this is not impossible. But the current helper has already trimmed using its initial rank; restore would need carefully chosen provisional placement and consistent re-trimming of hits, tuples, target index, origin and start cursor. Reusing/copying that path or splitting the helper is a larger patch than necessary for this contract. Do not select it without a concrete unmet requirement and approval; no latency benefit was measured here. |
| Rank and page only at the saved tuple | Avoids the correction but selects an old position even when lookup supplies a different current tuple, then inserts the current hit there. That is a different saved-anchor policy, not the requested effective-current-target landing. Reject without an explicit contract change. |

Using a map for rank is not a free substitute: presence alone does not establish that its tuple/membership matches this selected live target. Map readiness remains a performance option, not a coordinate or tuple authority added by this patch.
