## Kupua findings

### I6. Copying an untouched Taken date can move peers by one hour

**Data-changing defect; deterministic conversion probe.** In a London browser, the second occurrence of 01:30 on 25 October 2026 is `2026-10-25T01:30:00.123Z`. Form turns that instant into the unqualified local string `2026-10-25T01:30:00.123` and passes the displayed value to its batch arrow. `metadataIntent` parses that string back as **`2026-10-25T00:30:00.123Z`**. The source is excluded and stays correct; peers can all be wrong. Normal acknowledgement and readback can agree with that wrong instant. This is not a milliseconds truncation or a backend date-clearing problem.

[Display conversion](../../../../src/components/MetadataTextEditor.tsx#L61), [arrow input](../../../../src/components/MetadataTextEditor.tsx#L133), [intent conversion](../../../../src/stores/metadata-editor-store.ts#L44). The local `TZ=Europe/London` probe ran these conversion expressions, not a browser save. Details already has [offset-aware handling](../../../../src/components/MetadataTextEditor.tsx#L141). For an untouched source copy, carry the canonical instant. Add a Form regression with one peer and the second occurrence of the repeated hour; compare UTC instants, not displayed strings.

### I7. A visible digest can complete an uncertain upload without proving that attempt succeeded

**Real store probe; attribution issue, not file replay.** Start with a visible image, select the same file with a preset, and lose the transfer outcome. In the same tab, Recheck can find no loader status but find the existing image and count. The job becomes `complete` and the captured preset is submitted to the editor. Visibility proves the content ID is available, not that this attempt uploaded it. The image may be exactly the one the user meant; the UI nevertheless loses the distinction between availability and transfer provenance.

[Digest before transfer](../../../../src/lib/upload-commands.ts#L125), [missing-status fallback and follow-up](../../../../src/stores/upload-jobs-store.ts#L207), [real follow-up wiring](../../../../src/main.tsx#L88). A local harness ran the unmodified jobs store with mocked transfer/status/visibility dependencies and a recording follow-up: **before Recheck: uncertain, 0 callbacks; after: complete, 1 preset callback**. No HTTP write occurred. The [later recovery decision](../../gradually-growing-teeth.upload-workplan.md#L2915) explicitly allows unsent follow-ups; the mere existence of that callback is not a bug. Preserve “available; transfer unconfirmed” when no attempt evidence exists, and distinguish applying presets to already-available content from confirming a new upload.

### I8. Reload can remove the only indication of a failed upload follow-up

**Code-confirmed feedback loss.** A successful file with a rejected preset shows “Uploaded; metadata needs attention”. The live job has `phase: complete` and a follow-up marked `attention`. The [persisted attempt schema](../../../../src/lib/local-batch-storage.ts#L17) strips `followups`; restored activity [includes only attention phases](../../../../src/stores/upload-jobs-store.ts#L287). The [row](../../../../src/components/UploadProgress.tsx#L41) consequently has no remaining evidence of the failed preset. This is loss of a warning, not proof of lost image bytes. No durable draft store is needed: persist a small non-replayable attention/interrupted marker, or explicitly label follow-up history unavailable. Amend the existing [restore test](../../../../src/stores/upload-jobs-store.test.ts#L189) with a completed file and rejected preset.

### I9. Some accepted label names cannot be removed from Kupua

**Policy probe plus source trace.** Single `.` and `..` pass the nonblank [add schema](../../../../src/lib/grid-commands.ts#L11) and editor parsing. The real [removal predicate](../../../../src/lib/grid-mutation-policy.ts#L1) rejected both; `desk` passed. [Clear-all preflight](../../../../src/lib/grid-commands.ts#L301) refuses the entire list if any proposed removal URL is invalid. Thus one such member can also block clearing ordinary labels in that action. No service request was needed to prove the asymmetric domain. Validate new labels consistently at admission, including Upload presets; give a specific explanation for pre-existing unaddressable members. Do not relax path safety to force removal.

### I10. A stalled byte transfer can hold every later file indefinitely

**Liveness risk; source-confirmed absence of an application bound, incidence unmeasured.** The single [transfer loop](../../../../src/stores/upload-jobs-store.ts#L158) awaits each file. Signed storage PUT uses the user/lifecycle signal without the loader timeout; direct upload POST also has no application deadline ([transport](../../../../src/lib/upload-commands.ts#L82)). The five-minute observation window starts only *after* an accepted submission. A transfer that neither completes nor errors can therefore leave unrelated files waiting. Test with a held transfer and a second file. Prefer an explicit stop or a progress-aware stall policy; a fixed short timeout would punish valid large files. Never retransmit the uncertain file automatically.

### I11. A terminal label receipt can keep warning about departure after the work has ended

**Code-confirmed UX risk.** [EditLifecycle](../../../../src/components/LabelEditor.tsx#L240) scans the entire history and treats an acknowledged label with a deadline/unavailable observation as unfinished. Even a later explicit successful action does not remove the older receipt from [the store](../../../../src/stores/label-editor-store.ts#L151). Distinguish “leaving interrupts active work” from “leaving loses an unresolved receipt”; the latter may deserve a warning, but it should be understandable and acknowledgeable. A focused browser test should settle the old receipt, inspect its issue, complete a later action, and check the unload guard with no draft or request outstanding.

## Boundaries not to misdiagnose

- Mixed text committed as blank is explicitly a **clear** in the [UI decision](../../gradually-growing-teeth.editing-ui-decisions.md#L124); this is not an inferred accidental overwrite. Date clearing is intentionally unavailable ([GRID-025](../../bug-backlog.md#grid-025)). Make destructive intent clearer where needed without inventing new server semantics.
- `unknown` and `observed` can both be true. This is useful, not contradictory: the desired state exists but the client cannot attribute it to this write. A rights PUT and its derived POST likewise have separate outcomes. Acknowledged rights alone should not prompt replay of both steps.
- Do not infer that ordinary external lease removal always regresses the search clock. The [owning service model](../../../../../common-lib/src/main/scala/com/gu/mediaservice/model/leases/LeasesByMedia.scala#L32) dates the newest surviving record, but [Thrall removal](../../../../../thrall/app/lib/elasticsearch/ElasticSearch.scala#L698) sets the indexed collection's event timestamp even when removing the final member. A fixture using the owning-service timestamp for normal indexed reads is not evidence of that browser bug.
