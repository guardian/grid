# Config

The Grid has different config files depending on the service and usage e.g. the Guardian or BBC-specific features.
[`GridConfigLoader.scala`](https://github.com/guardian/grid/blob/main/common-lib/src/main/scala/com/gu/mediaservice/lib/config/GridConfigLoader.scala) loads the configs, which get parsed and turned into a tree of config by a function in this library (https://github.com/lightbend/config) which will recursively merge the trees.

#### [`application.conf`](https://github.com/guardian/grid/blob/3fb1d936f82a0cd02a2a3c4293b680f7f8f5caf5/common-lib/src/main/resources/application.conf)

The file lists configs that every user and service should have. This file should provide good defaults for grid features where required. This file has the lowest priority and keys will be overridden if set in other files.

### Other config files

Other config files will be read from `$HOME/.grid/` (when running locally) or `/etc/grid` (when deployed, as determined by the contents of `/etc/grid/stage`).
For local development, files will be generated by the [generate-config script](/dev/script/generate-config). It is up to the implementor to determine how to load config files onto deployed instances - we at the Guardian currently fetch files from S3 in a [UserData script](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/user-data.html).

This file will be packaged by sbt-native-packager, available once installed on the destination instance and automatically loaded by Play.

> **Note**
> Currently this is the only file that is loaded at Play's first initialisation. Some play settings will only take effect if set in this file.

#### `<configRoot>/<stage>/common.conf`
Anything that's specific to an organisation and to a stage, but is common across all the services. Keys set here will override those set in `application.conf` but be overridden by the service-specific configs.

#### `<configRoot>/<stage>/<service>.conf`
Service-specific configs. These will override all other config files.

## Config documentation

### Sentry

Kahuna uses the Sentry browser SDK to report JavaScript exceptions and console errors when
`sentry.dsn` is configured. AngularJS exceptions retain the normal Angular handler; failed HTTP requests
are excluded from exception reporting. Angular's delegated logging is kept, but Sentry events
generated by that delegate are discarded to avoid duplicate reports and console reports of filtered HTTP errors.
Other console warnings/errors are still captured. The `grid.instanceId` event context identifies the Kahuna
instance that served the page, not an individual user or browser session.

| Setting | Default | Meaning |
| --- | --- | --- |
| `sentry.dsn` | unset | Enables reporting; absent or unusable values disable it. |
| `sentry.localOptIn` | `false` | Required to allow reporting in DEV, even with a DSN. |
| `sentry.console.levels` | `["error"]` | Browser console events to capture; `[]` disables console capture. Previously both warnings and errors were captured. |
| `sentry.user.mode` | `anonymous` | Browser user identity: a salted identifier, or `email` when explicitly approved. |
| `sentry.user.salt` | unset | Secret HMAC salt; without it anonymous mode sends no personal user identifier. Never commit or expose this salt to the browser. |
| `sentry.tracesSampleRate` | `0` | Fraction of browser/server transactions sampled, from 0 to 1 inclusive. Zero disables tracing; invalid/non-finite values fail startup. |
| `sentry.replay.onErrorSampleRate` | `0` | Fraction of browser sessions sent as replay after an error, from 0 to 1 inclusive. Zero omits the replay integration. |

Events include the Grid stage as their environment and the build commit as their release.
Kahuna derives its CSP connection allowance from the configured DSN. Configure the DSN in your
deployment configuration, not in the repository.

Production browser builds generate hidden source maps. CI uploads them when `SENTRY_AUTH_TOKEN`,
`SENTRY_ORG` and `SENTRY_PROJECT` are supplied, using `BUILD_VCS_NUMBER` as the release identifier.
The same build identifier must be used by SBT so runtime events match the uploaded maps. Maps are
deleted after upload before packaging. Without a token (including fork builds), upload is skipped;
hidden maps are still generated locally. A token with incomplete upload configuration fails the build
and lists the missing setting names without logging their values.

All services extending `GridComponents` also report uncaught Play server exceptions with the same
configuration. Events carry service (`app`), stage, release and request ID tags. Request metadata is
limited to method, route/URL and User-Agent; cookies, request bodies and other headers are not attached.
Client errors remain with Play, and a reporting failure must not change the HTTP response.

Browser identity is resolved on the server. The `anonymous` mode sends a stable pseudonymous
identifier, not the user's email. Events remain linkable to the same user, and anyone holding the
secret HMAC salt can reproduce identifiers from candidate email addresses. Rotating the salt breaks
correlation. Machine identities are sent as service IDs.
Email mode sends personal data to Sentry and requires data-protection approval before enabling.
These identity controls do not add authenticated user identity to server error events.

Tracing is opt-in. The browser propagates traces only to configured internal service URIs. Services
continue incoming `sentry-trace`/`baggage` headers and use method/route patterns as transaction names,
excluding management endpoints, assets and unrouted requests. Request attributes carry transactions
across asynchronous processing rather than thread-local scopes. A shared request-local holder is
created before filters run, so Play's outer error handler can link exceptions to the transaction
even though filters pass modified request copies downstream. Transactions finish on successful
responses, failed futures and synchronous downstream exceptions; Play still handles error responses.
If a deployment restricts CORS request headers, allow `sentry-trace` and `baggage`.

Replay is separately opt-in and error-triggered only: continuous session sampling is always zero.
Text masking and media blocking are mandatory because Grid displays unpublished imagery and personal
data. Before enabling replay, obtain data-protection approval and inspect output with representative
screens to confirm sensitive content is not included.
